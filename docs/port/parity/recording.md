Spec: `docs/port/specs/recording.md`. Section 8 has 195 items, section 7 has B-1 to B-32, section 6 lists the tests to carry over. Every row has an owner package (R1 to R12). Status words: `done`, `improved` (a section 7 fix or a recorded decision changed the behavior), `dropped`, `open` (a later package owns it), `pending-real-validation`.

Owner decision 2026-11-03 scope cuts that touch this module are marked `dropped` with the reason "owner decision 2026-11-03, may return later". On-disk keys for them are still read and rewritten.

## Decisions

- R1-D1: the readiness resolver takes `RecordingSetupPorts` (settings, model file exists, CLI on PATH per kind, engine ready). The main-process adapters belong to R5.
- R1-D2: a settings file that selects Xai loads unchanged; setup yields `summaryProviderRemoved: true`, `summaryProviderChosen: false`, never ready. The UI shows the existing `Ui_SummaryProviderXaiRemoved` message.
- R1-D3: pure rules return catalog keys and args, not finished strings, so a language change relabels without recomputing.
- R1-D4: the B-17 dead branch (`if (dialog.CanRecord) return true` in EnsureReady, and the "Done" button logic) is not ported. The R9 loop is: ready -> true; else dialog -> cancel -> false; else run missing steps and re-evaluate.

## Bugs fixed

- R2: B-3 (previous WAV kept), B-6 (Jev, notes, attendees, calendar ids, template carried over), B-7 (old summary kept until the new one succeeds), B-11 (recoverable first-save failure), B-18 (accurate engine message), B-28 (repository audio path reused).
- B-12 (domain half): typed `severity` on `CaptureNotice`. The renderer half is R9.
- B-20: one provider parse rule (`parseSummaryProvider`) for readiness. The pipeline and live ask must adopt it (R2, R3, R7).

- B-17: dead branch not ported (see R1-D4).
- R3: B-1 (both languages' placeholder titles replaced), B-21 (background summary cancellable: cancelBackgroundSummary).

## Decisions (R3)

- R3-D1: the summary stage lives in `pipeline/summary-stage.ts` and calls the summaries module through `SummaryService.generate` (and `SummaryProviderResolver` for the safety net), never a provider. `GenerateRequest` gained optional `rawNotes` and `templateInstructions` so the pipeline passes live notes and its own template text. `RecordingPipelineDeps.summary` is optional; without it a run ends at `transcript-saved` (R2 behavior).
- R3-D2: when this run already stored the transcript (step 4), the failure and cancel handlers do not save it again. The C# saved it again, which could overwrite edits made while a summary ran for minutes.
- R3-D3: a Xai selection shows `Ui_SummaryProviderXaiRemoved` even when a transcription warning exists, because it needs the user to act. Other not-ready cases show the warning or `Status_DoneNoSummary`.
- R3-D4: after the hand-off the background summary has its own cancel source, also linked to the run's cancel signal. A cancelled summary ends with `Status_CancelledTranscriptSaved` ("Cancelled. Transcript saved (no summary)."), keeps the transcript, and leaves no summary.
- R3-D5: new outcome kinds on `PipelineOutcome`: `completed`, `no-summary`, `summary-failed`, `summary-cancelled`, `failed`.
- R3-D6: tests were written after the code in one pass (no separate RED run); they cover each branch with a real SummaryService and fake provider.

## Decisions (R2)

- R2-D1: the request type is `PipelineRequest` (not `RecordingPipelineRequest`, which `transcription/retranscription.ts` already exports with string dates). Times are epoch milliseconds. R6 adapts the re-transcription request to it. Messages are `Message` keys, so a language change relabels them.
- R2-D2 (B-3): the pipeline never touches files. `PreviousAudioKeeper.keep(path)` is a port; R5 implements it by renaming to `<stem> (previous).wav` beside the old file. Without a keeper, or if it throws, the old file stays and its path is reported as `previousAudioPath`. The old transcript and summary stay paired with the new audio until replaced (the 3.7 rule), only the old WAV is kept.
- R2-D3 (B-7): "same audio" means the stored record's audio path equals the request's (case-insensitive). Only then does the transcript save keep summary, action items and provider. A new take over a different WAV still writes none (item 140).
- R2-D4: the `Part 1` result is `PipelineOutcome`; `transcript-saved` carries the transcript, stored record, audio path and the transcription warning for R3's summary stage. Cancellation and first-save failure are handled here; the generic failure and summary-stage handlers are R3.
- R2-D5: clock skew (`pausedDuration`) is passed to the offline pass as `clockSkewMs`; the ported engine ignores it because it never had an effect (transcription B1).
- R2-D6: a failed first save with a draft carries on (the draft is not lost); with no draft the outcome is `first-save-failed` and the pass does not run.

- R4: B-24, B-26, B-30 (see rows). Run host in `packages/core/src/recording/runs/` (`RecordingRuns`, `PipelineRun`).

## Decisions (R4)

- R4-D1: statuses are `StatusLine = Message[]`; the capture-failure prefix and the soft warning are separate messages, so each is translated on its own.
- R4-D2: `saveAndFinishForClose(stop)` takes the stop as a callback and the 30 s grace through an injected `schedule`; `complete` is queued with an injected `defer` (microtask by default).
- R4-D3: R4 tests were written after the code (no separate RED run).

## Decisions (R5)

- R5-D1: `RecordingService` (`apps/desktop/src/main/recording/recording-service.ts`) owns the take; `RecordingTakes` stays the capture half and gained `StartOptions.allocate`, the WAV `path` in its start result, partial-file removal and live stop on a failed start. `composeRecording` builds the pipeline (offline pass, previous-audio keeper, summary stage) and the service; `index.ts` only calls it.
- R5-D2: new channels `recording.*` (contracts `recording.ts`). The old `audio.recording.*` channels stay until R9 moves the page; they bypass the service, so the page must use only one set.
- R5-D3: the state event carries no transcript text. `recording.liveText` carries the canvas text (highlights applied through `HighlightedLiveText`, which reuses its result until the text or the marks change). The elapsed time travels as `elapsedMs` at `elapsedAsOfMs` plus `isTicking`, so main sends no timer ticks and the page counts locally; the level meter still uses `audio.recording.level` and is zero while paused.
- R5-D4: status entries carry a typed `severity`: from the capture notice itself, `error` for `Error_*` keys and `Ui_ProcessLoopbackUnsupported`, `warning` for `Ui_SummaryProviderXaiRemoved`, else `info`.
- R5-D5: `recording.start` takes `microphone: null` and no `processId` to mean "restore the remembered ones" (B-23); `processId: null` is all system audio.
- R5-D6: the live pass is started with the time before the model loads, as the engine needs a value up front; the meeting `recordedAt` is the capture start. The live draft `Recorded` header can differ from it by the model load time (minute precision).
- R5-D7: a stem whose Markdown is the same meeting is accepted only when no WAV sits beside it, so a re-recording never writes over the first take audio.
- R5-D8: `cancelProcessing({ meetingId })` cancels the background summary when an id is passed (B-21), else the foreground run.
- R5-D9: the service tests were written with the code in one pass, using a real `AudioController` and `RecordingTakes` over a fake audio worker host, the real pipeline and a scripted meeting store (the fake-native service test); no separate RED run.
- R5-D10: the clock skew is not sent to the live pass (transcription decision 5); `pausedDurationMs` still reaches the pipeline request.

## Decisions (R6)

- B-19: the file time is the end of the take, `recordedAt = fileTime - duration`, `endedAt = fileTime`. An unreadable or zero file time means now, also read as the end. The WAV stem uses the date of the file time (the length is only known after the conversion), so a file that crosses midnight can carry the end date in its name.
- Import goes through `recording.import` `{ title, folderId, path }`. Main stats the file itself, so the page no longer passes a time. `audio.import.pickFile` stays the picker; `audio.import.run` and `RecordingTakes.importPicked` are the old path and should go when R9 moves the page over.
- Cancel of an import in progress uses `recording.cancelProcessing` with a null id; it stops the conversion, removes the partial WAV and shows `Status_ProcessingCancelled`, not an error. The gate is Preparing during the conversion, so the page shows its cancel from the `Status_Importing` status.
- The take-notes request is consumed in main (`startTakeNotesRequests`), so it works with no Record page open. The page does not need to consume it. Calendar event ids are ignored (owner decision 2026-11-03, may return later); the request is always a blank take.
- The call prompt already hides when the capture flag rises (meeting-detection-controller W14), so starting any recording dismisses it with no extra code.
- Close protection: `before-quit` and the main window `close` event consult `settings.exitGates.mayExit()` first, and the recording gate is `CloseGuard.mayClose()`. With no window to show a dialog the close is refused (stay open). The Restart service uses the same gates.
- `processAudioFile(meetingId | null, path, request)` is the entry for re-transcription through the full pipeline. `pipelineRequestFromRetranscription` adapts `createRetranscriptionRequest` to `PipelineRequest`. The existing transcription-module re-transcription (transcript only, `summarizeForPipeline`) is unchanged.

## Accepted lossy cases (R8)

Tested in `notepad-markdown.test.ts`. The meaning is kept; the spelling is the editor's, and only when the user edits the notes in the editor:
